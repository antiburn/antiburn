**Status:** implemented

## Why this is a second plan

The first attempt ran in a worktree cut from the local `main`, which is the
pre-rewrite history: `git merge-base` with `origin/main` was empty and the base
was 1,021 files behind. On that stale tree the `insights` engine looked like the
pane's private backend, so the approved plan deleted it. On the real `main` that
would delete a shipped feature. This plan is scoped to what `origin/main`
actually contains. The old branch stays local and unpushed as reference.

## What changed under us

`antiburn_local::insights` is now shared infrastructure:

- **Burn Checks** — `views/main-window/BurnChecksView.tsx`,
  `popover/ChecksView.tsx`, `components/burn-checks/`, and eleven Tauri commands.
- **Session hygiene badges** — `insights/badges.rs` exports `session_badges`,
  consumed at `commands.rs:2132`.
- **Auto-fix** — `remediation/mod.rs` and `remediation/watch.rs` read
  `insights_report::{list_current_findings, reduce_report_blocking, …}`.
- `lib/insightsIpc.ts` has 48 importers.

So the engine stays. Only the Settings pane comes out.

### Keep, and why

- **`insights_ipc.rs`** — `InsightsController` also serves `checks_report()` for
  the popover and main window. Only `settings_report()` goes.
- **`insights_report.rs`** — read by `remediation/`, `store/mod.rs:2011`, and
  the worker's tests.
- **`insights_worker.rs`** — the evidence queue drain. Keeping its name this
  time: on `main` it is reached by `get_checks_report` too, and a rename would
  collide with in-flight work for no gain here.
- **`crates/antiburn-local/src/insights/`** — Burn Checks, badges, auto-fix.
- **`InsightsNotAssessedReason`** — `lib/presentation/sessionHygiene.ts` uses it.

## Decision taken: three analytics streams

`get_insights_report` is the **only** caller of three recorders
(`commands.rs:1606-1608`):

```rust
crate::analytics::record_unrecognized_records(&app, &report.unrecognized_records);
crate::analytics::record_quota_incidents(&app, &report.quota_pressure);
crate::analytics::record_provider_incidents(&app, &report.provider_incidents);
```

`get_checks_report` does not call them. Delete the pane as-is and antiburn stops
emitting `unrecognized_records`, `quota_incidents`, and `provider_incidents`
entirely — the pane was carrying telemetry that has nothing to do with the pane.

**A, as recommended.** The three calls moved into `get_checks_report`. It runs
the same reduction over the same `ReducedReport`, from surfaces that open far
more often than Settings, so coverage improves rather than degrades. Each
recorder compares the outcome against the one it last sent
(`unrecognized_outcome_is_new`, `quota_incident_bucket_is_new`,
`provider_incident_bucket_is_new`), so the more frequent call site repeats no
events.

## Found while building, and done

Three things the pane reached that the plan did not list. Each one is dead or
broken the moment the pane goes, so each one comes out with it.

| What | Where | Why |
|---|---|---|
| The Coverage details button | `burn-checks/BurnChecksHeader.tsx`, `BurnChecksView.test.tsx` | Burn Checks deep-linked into the pane. With no pane, the button leads nowhere. |
| The `insights` state surface | `lib/ipc.ts`, `lib/surfaceExposure.ts` + test, `analytics/event.rs` | `InsightsSession` was the only exposer, so `StateSurface` collapses back into `Surface` and the "report state but not a view" exception goes. |
| `SettingsPane::Insights` | `analytics/event.rs`, `analytics/mod.rs` | The pane is also the only settings pane that counted as deliberate activity. |

Two more followed from the deletions: `InsightsController` loses its settings
consumer (`settings_report`, `release_settings`, `Consumers.settings_active`),
and `settings.rs` loses the `cancel_insights` hook it fired when the window was
destroyed. Three dto stringifiers (`detector_id_str`, `quota_limit_kind_str`,
`provider_incident_kind_str`) were reached only by the removed conversion.
